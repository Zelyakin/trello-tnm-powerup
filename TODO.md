## ⚡ Оптимизация запросов к Supabase

### 7. Перевести оставшиеся запросы на batch-режим
В прошлой итерации мы уже сильно сократили число запросов (см. CLAUDE.md "Performance Notes" — с 48 до 12 на загрузку доски). Но часть мест оставалась с N+1 паттерном или избыточными вызовами.

#### 7.1. ✅ `getAllDataForExport()` — устранён N+1
Было: после `GET /cards` шёл **последовательный** цикл `for (const card of cards) { await GET /time_entries?card_id=eq.{card.id} }` — для доски на 50 карточек 51 запрос подряд.

Стало: 2 **параллельных** запроса (`Promise.all`) — список карточек и записи времени через PostgREST embedded resource (`cards!inner(trello_card_id) + cards.board_id=eq.X`). JOIN выполняется на стороне Supabase, никаких `in.(cardIds)` → нет лимита длины URL независимо от размера доски. Группировка по `trello_card_id` на клиенте, UUID Supabase наружу не утекают. Пустые карточки сохраняются как `timeEntries: []` (для UI-флага "Include empty cards").

#### 7.1.1. ✅ `getBoardStats()` — снят URL-лимит и ушёл лишний запрос
Было: 3 запроса (`/boards` → `/cards` → `/time_entries` с `in.(cardIds)`). При >500 карточках на доске `in.(...)` упирался в лимит длины URL у PostgREST (~8 КБ).

Стало: тот же приём, что и в 7.1, но даже агрессивнее — `/cards` вообще не нужен (статистика считается только из entries: totals, distinct card_id, contributors). 1 запрос к `/time_entries` через embedded JOIN (`cards!inner(id) + cards.board_id=eq.X`). Пустая доска / пустой период → `entries=[]` → корректный нулевой ответ без специального early-return. **Итог: 1 запрос warm / 2 cold.**

#### 7.2. ✅ Бейджи: N запросов на N карточек — сделано 2026-07-31

**Реализовано:** `prefetchBoardBadges()` в [js/supabase-api.js](js/supabase-api.js), точка входа — `getCardDataForBadge(cardId, boardId)`; `board.id` пробрасывает [js/storage.js](js/storage.js). Все нюансы из плана ниже учтены: метка префетча ставится **после** заполнения кэша, promise deduplication на месте, `invalidateCardCache()` сбрасывает метки (иначе только что обновлённая карточка попала бы под правило «нет в префетче → ноль»), при отсутствии `boardId` или падении префетча работает старый пер-карточный путь.

**Замерено:** реальная доска на 270 карточек — 2 запроса / ~4 КБ вместо ~270 запросов / ~264 КБ. Открытие доски теперь **3 запроса при любом размере доски** (`/boards` + `/cards` + `/board_settings`).

Проверено на моке (5 сценариев): холодный старт с 5 параллельными callback'ами, повтор в пределах TTL (0 запросов), неизвестная карточка (0 запросов, 0 минут), корректное значение после мутации + инвалидации, оба фолбэка. Описание в CLAUDE.md → «Badge Prefetch (v3.5)».

<details>
<summary>Исходный план (для истории)</summary>

[js/client.js:22-41](js/client.js:22) — Trello вызывает callback `card-badges` отдельно для каждой карточки, и каждый вызов делает свой `GET /cards?select=time_minutes&trello_card_id=eq.{id}`. Для доски на 100 карточек = 100 запросов к `/cards`.

**Идея:** при первом обращении к бейджу префетчить агрегаты для **всех** карточек доски одним запросом и положить в `_cardDataCache`:
```javascript
// При первом вызове getCardDataForBadge на этой доске:
const allCards = await this.request(
  `cards?select=trello_card_id,time_minutes&board_id=eq.${supabaseBoardId}&time_minutes=gt.0`
);
allCards.forEach(c => this._cardDataCache.set(`badge_${c.trello_card_id}`, {
  data: { timeMinutes: c.time_minutes || 0, history: [] },
  timestamp: Date.now()
}));
```
Все последующие 99 callback'ов будут попадать в кэш. **100 запросов → 1 запрос.**

Добавка по итогам замеров 2026-07-30 (см. «Трафик» ниже) — фильтр **`&time_minutes=gt.0`**: бейдж при нуле не рисуется ([js/client.js:30](js/client.js:30)), а по проду 6 726 карточек с временем из 65 416 — **90% строк были бы нулями**. Карточка, которой нет в префетч-карте, и так корректно отдаёт 0 текущим фолбэком, так что фильтр бесплатен. На средней доске ответ падает с ~42 строк до ~5.

⚠️ Нюансы:
- Нужен флаг "префетч уже был для этой доски в этом TTL-окне" (`_boardPrefetched: Map<boardId, timestamp>`), иначе каждая карточка снова запустит full-board запрос.
- Promise deduplication (как в `getBoardId()`) обязательна — иначе при параллельном вызове 100 callback'ов мы получим 100 одинаковых full-board запросов.
- Размер ответа растёт линейно с числом карточек, но `time_minutes` — это int, ответ остаётся компактным даже для больших досок.
- Trello может вызывать badge callback и для карточек, которых ещё нет в Supabase (новые карточки) — для них должен возвращаться `{ timeMinutes: 0 }`, что и так корректно работает через текущий fallback.
- Кэш префетча живёт в контексте `client.js` (iframe доски); попапы/card-back его не видят — это отдельный п.18.

</details>

## 📉 Трафик к Supabase (замеры 2026-07-30)

Цель — остаться в бесплатном плане (5 ГБ egress/мес), свой стор поднимать не хочется.

**Что показали замеры на проде:**

| Метрика | Значение |
|---|---|
| Заголовки ответа на типовой badge-запрос | **954 B** |
| Тело того же ответа | **23 B** (`[{"time_minutes":1500}]`, gzip включён) |
| CORS-preflight | отдельный OPTIONS на каждый уникальный URL, `access-control-max-age: 3600` |
| boards / cards / time_entries / board_settings | 1 543 / 65 416 / 17 712 / 993 |
| Карточек с `time_minutes > 0` | 6 726 (**10%**) |

**Главный вывод: трафик определяется числом запросов, а не объёмом данных** — полезная нагрузка ~2% от того, что едет по проводу. Часть заголовков схлопывает HPACK в рамках одного соединения, но динамические (`date`, `cf-ray`, `sb-request-id`, `set-cookie __cf_bm` ~250 B) — нет. Поэтому всё ниже меряется в **запросах**, а не в килобайтах.

Средняя доска: ~42 карточки, из них с трекингом ~5. Открытие такой доски на холодном кэше ≈ 42 OPTIONS + 42 GET ≈ **65 КБ ради <1 КБ полезных данных**.

Порядок работ по убыванию эффекта:

### 14. ✅ Префетч бейджей — сделано 2026-07-31, детали в п.7.2
~90% всего трафика Power-Up'а. Открытие доски: N+2 запроса → **3 запроса при любом размере**. На реальной доске в 270 карточек — 264 КБ → 4 КБ (**~65x**).

### 15. Путь добавления записи: 5 запросов → 2
Сейчас `addTimeEntry` ([js/supabase-api.js:231](js/supabase-api.js:231)) делает: SELECT карточки → SELECT на проверку дубликата → INSERT → SELECT всех `time_minutes` карточки → PATCH агрегата.
- Пересчёт агрегата (`updateCardTotalTime`, [js/supabase-api.js:295](js/supabase-api.js:295)) унести в **триггер Postgres** `AFTER INSERT/UPDATE/DELETE ON time_entries` → `UPDATE cards SET time_minutes = ...`. Минус 2 запроса на каждую мутацию **и** минус целый класс рассинхрона: сейчас консистентность агрегата держится на дисциплине вызовов из клиента (см. CLAUDE.md, «Why Aggregates in cards Table?»).
- SELECT на проверку дубликата не нужен — есть `UNIQUE(card_id, trello_entry_id)`, достаточно ловить 409 (обработка дубликата в `catch` уже написана).
- То же касается `deleteTimeEntry` — после триггера из него уходит `updateCardTotalTime`.
- ⚠️ После перехода на триггер убрать ручной вызов `updateCardTotalTime`, иначе он останется лишним round-trip'ом, который просто перезапишет то же значение.

### 16. `card-back` качает всю историю, чтобы показать 5 записей
[views/card-back.html:157](views/card-back.html:157) — `timeEntries.slice(0, 5)`, при этом `getCardDataFull` тянет **все** записи карточки. Карточка со 100 записями = ~23 КБ на каждое открытие карточки ради 5 строк.
Нужен облегчённый путь: `&order=created_at.desc&limit=5` для card-back, полная история — только в попапе card-detail (там она реально нужна: удаление записей).
⚠️ Кэш общий (`full_${cardId}`) — при разных лимитах нужны разные ключи, иначе card-detail подхватит обрезанные 5 записей из кэша card-back.

### 17. В истории едут два поля, которые UI не читает
`getCardDataFull` ([js/supabase-api.js:191](js/supabase-api.js:191)) селектит `trello_member_id` и `trello_entry_id` — ни то, ни другое не используется ни в card-back, ни в card-detail (удаление идёт по `created_at`, отображение — по `member_name`). Это ~30% веса строки: 230 B → ~160 B.
⚠️ Проверить перед удалением, что `timestampId`/`memberId` не читает ничего в `views/` — при последней проверке (2026-07-30) не читало.

### 18. Кэш изолирован по iframe'ам
`card-back.html`, `card-detail.html`, `board-stats.html`, `export-time.html`, `settings.html` — **разные JS-контексты**, у каждого свой холодный `_boardIdCache`/`_boardSettingsCache`. Открытие card-back = +2 запроса (`/boards` + `/board_settings`) сверх двух своих; то же на каждое открытие попапа.
Решение: перенести оба значения в Trello board shared storage (`t.set('board','shared', …)`) — трафик Trello бесплатный и общий для всех iframe'ов. UUID доски вообще неизменен (можно хранить бессрочно), настройки меняются раз в год и уже имеют механизм инвалидации через `tnm-settings-updated`.

### 19. `getBoardStats()` — агрегация на клиенте
[js/supabase-api.js:410](js/supabase-api.js:410) качает **каждую** запись периода, чтобы посчитать 4 числа, причём в каждой строке едет дубль `"cards":{"id":…}` — артефакт `!inner`, ~50 B мусора на строку.
Решение — **RPC-функция** в Postgres (`POST /rest/v1/rpc/board_stats`), ответ ~200 B вместо N×135 B.
⚠️ PostgREST-агрегаты в запросах (`select=member_name,time_minutes.sum()`) на проекте **отключены** — проверено, отдаёт `PGRST123 "Use of aggregate functions is not allowed"`. Поэтому именно RPC, а не select-агрегаты (либо сначала включить их в настройках проекта).

**Ожидаемый суммарный эффект:** п.14 + 15 + 18 — примерно день работы и **20–40x** по трафику. При лимите 5 ГБ/мес это разница между ~77 тыс. открытий доски и почти миллионом.
**Статус:** п.14 сделан 2026-07-31 (основной кусок эффекта), остаются 15–19.

### 10. ✅ Имена архивных/удалённых карточек в CSV (Trello REST)

Было: имя карточки бралось только из `t.cards('all')`, который возвращает **лишь открытые** карточки доски. Архивные и удалённые выгружались как `Card <id>` и были неотличимы друг от друга.

Стало ([views/export-time.html](views/export-time.html)): для карточек, которых нет в `t.cards('all')`, имя достаётся через **Trello REST** (`GET /1/cards/{id}?fields=name,closed`):

- `200 + closed:false` → `<name>` (карточка открыта — напр. перенесена на другую доску)
- `404` → `[deleted] <id>`
- ошибка/отказ от авторизации/нет ключа → фолбэк `Card <id>` (экспорт не ломается)

Авторизация **opt-in, ленивая и read-only**: резолв включается галкой «Resolve names of archived/deleted cards» в форме экспорта (по умолчанию **выкл**). Без галки экспорт вообще не трогает REST/авторизацию, off-board → `Card <id>`. С галкой и при наличии off-board карточек → `authorize({scope:'read', expiration:'30days'})` вызывается прямым кликом (иначе браузер блокирует попап). Токен хранит клиентская библиотека Trello (member-private), у нас не оседает. Статус кодируется префиксом к имени — отдельной колонки нет (по решению).

⚠️ **UX-нюанс (решён):** `read`-скоуп у Trello даёт токен на чтение **всего аккаунта** (пер-бордового скоупа в этом флоу нет), consent-экран пишет «доступ к аккаунту» — на месте пользователя это отпугивает. Решение: резолв сделан **opt-in** (дефолтный экспорт авторизацию не триггерит вообще); текст промпта заранее предупреждает про account-level; токен на 30 дней с отзывом в любой момент. Промпт при показе прячет форму фильтра (не уезжает под фолд), debug-панель убрана из UI в консоль.

✅ **Разовая настройка выполнена:** публичные API-ключи вставлены в `TRELLO_API_KEY` ([views/export-time.html](views/export-time.html)) — по ключу на каждый деплой, выбор по `location.hostname` (prod `pages.dev` / dev `github.io`), в Allowed origins каждого ключа прописан только его origin. См. README → Configuration → Trello REST API.
