# План: настоящая авторизация вместо anon-ключа (TODO п.13)

Составлен 2026-08-29. Фазы 0 и 1 (код) выполнены, дальше — деплой и выкат.

## Суть

Клиент ходит в PostgREST со статическим `SUPABASE_ANON_KEY`
([js/supabase-api.js:24](js/supabase-api.js:24)). Ключ доказывает «я клиент этого проекта», но не
доказывает **на какой доске открыт Power-Up**, а фильтры в PostgREST пишет сам клиент — значит
`board_id=eq.<чужой>` ничем не отличается от своего.

Решение — обмен токена:

```
iframe: t.jwt() → POST /functions/v1/trello-auth   (Supabase Edge Function, verify_jwt=false)
                    ├ проверяет RS256-подпись Trello (публичные ключи api.trello.com, кэш 4ч)
                    ├ сверяет idPlugin ∈ {prod, dev}
                    └ выпускает HS256-токен на 1 час:
                        { role:'authenticated', aud:'authenticated', sub:idMember,
                          trello_board_id:idBoard, trello_member_id:idMember }

iframe: все запросы к PostgREST идут напрямую с этим токеном (горячий путь без прокси)
RLS:    board_id = current_board_id(), где current_board_id() читает auth.jwt()->>'trello_board_id'
```

Ключевая мысль: **мы не строим авторизацию, её уже построил Trello.** `t.jwt()` отдаёт JWT,
подписанный приватным ключом Trello (RS256), с клеймами `idPlugin`/`idBoard`/`idMember`. Подделать
его из devtools нельзя. Не хватало только серверной точки, которая проверит подпись — ей
становится Edge Function.

### Почему Edge Function, а не Cloudflare Pages Function

- **Снимается асимметрия деплоев.** Прод на `pages.dev`, дев на `github.io`. Функция на Cloudflare
  жила бы на одном из этих origin'ов, и второй ходил бы к «чужому». Функция на `*.supabase.co`
  внешняя для обоих одинаково.
- Секрет подписи, БД и политики — в одном вендоре.
- Free-план: 500 000 вызовов/мес; нам нужен ~1 вызов на открытие iframe при TTL токена в час.

### Почему нельзя проще

- **Trello как Third-Party Auth провайдер Supabase — нельзя.** Список провайдеров фиксирован
  (Clerk, Firebase, Auth0, Cognito, WorkOS). Даже будь generic-вариант: TPA требует OIDC Discovery +
  JWKS с `kid`, а Trello отдаёт голый массив PEM. И в токене Trello нет клейма `role`,
  обязательного для PostgREST.
- **Проверять RS256 в Postgres — нельзя.** `pgjwt` в Supabase отсутствует, `pgcrypto` не проверяет
  RSA-подписи, `pgsodium` — Ed25519.
- **Только RLS без сервера** (знаешь id доски → имеешь доступ) — отвергнуто: id досок лежат в URL,
  а удалённый из команды человек сохранял бы доступ навсегда.

## Фаза 0. ✅ Сверка схемы (2026-08-29)

README описывал схему неверно — фактические типы:

| Таблица | PK | Ключевые поля |
|---|---|---|
| `boards` | `id uuid` (`gen_random_uuid()`) | `trello_board_id **text**` (не uuid!) |
| `board_settings` | `id **integer** (serial)` | `board_id uuid → boards.id` |
| `cards` | `id uuid` | `board_id uuid → boards.id`, `trello_card_id text` |
| `time_entries` | `id uuid` | `card_id uuid → cards.id` |

Состояние защиты на момент сверки:

- RLS: `enabled` на `boards`/`cards`/`time_entries`, **`DISABLED` на `board_settings`**.
- Политики: по одной `"Allow all" FOR ALL **TO anon** USING (true)` на первых трёх таблицах.
- Гранты: **и `anon`, и `authenticated`** имеют всё, включая `TRUNCATE`.

**Главное следствие — у роли `authenticated` сейчас нет ни одной политики.** Значит порядок
выката обратный тому, что казался очевидным: политики для `authenticated` надо завести **до**
перевода клиентов, иначе первый же клиент с токеном получит пустые ответы. Зато и окно поломки
исчезает: до финального шага работают оба пути одновременно.

Отдельная мелочь с последствиями: `board_settings.id` — единственный `serial` в схеме, поэтому
роли нужен грант на последовательности, иначе INSERT настроек упадёт на правах.

README поправлен по факту.

  (перехватывает `Deno.serve`, ключи Trello подменяются своей парой RSA).

Покрыто тестом: CORS для своего/чужого origin, happy path, состав минченного токена (role, aud,
sub, TTL, отсутствие утечки `idPlugin`), чужой `idPlugin` → 403, протухший токен → 401, подпись
неопубликованным ключом → 401, мусор → 401, пустое тело → 400, неполные клеймы → 401.

**Осознанный компромисс, зафиксированный тестом:** ключ, который Trello убрал из выдачи, продолжает
приниматься до истечения TTL кэша (4 часа). Это стандартная цена кэширования ключей; уменьшать TTL
ради этого не стоит.

Задеплоено на `tpzbvdyxmzqweoghtgzp`, секреты залиты. Проверено `curl`'ом на живой функции:
мусор вместо токена → `{"error":"invalid_trello_token"}` 401 (**наша** ошибка, а не гейта —
значит `verify_jwt = off` применился, и секреты подхватились: иначе был бы `server_misconfigured`),
пустое тело → 400, CORS со своего origin → 204 + эхо, с чужого → без заголовка.

Осталось: сквозная проверка с **реальным** Trello-JWT — она произойдёт сама при тестировании
дев-клиента (Фаза 4, шаг 4).

## Фаза 2. ✅ Клиент: получение и хранение токена (код готов)

Точка врезки одна — `SupabaseAPI.request()` ([js/supabase-api.js:19](js/supabase-api.js:19)):
вместо `Bearer ${ANON_KEY}` подставляется минченный токен.

Проблема: `request()` вызывают методы, которым `t` не передаётся (`getCardDataForBadge(cardId, boardId)`,
`getBoardSettings(boardId)`), а тащить `t` через все сигнатуры — большой диф. Решение — регистрация
контекста один раз:

```javascript
SupabaseAPI.useTrelloContext(t);              // один раз на JS-контекст

// внутри request():
headers.Authorization = `Bearer ${await this._getAccessToken()}`;
headers.apikey = this.SUPABASE_ANON_KEY;      // остаётся: это «пропуск на порог» PostgREST
```

Где регистрировать (везде `t` уже есть):

| Контекст | Файл |
|---|---|
| iframe доски (бейджи) | [js/client.js:5](js/client.js:5) — `t` есть в каждом колбэке |
| card-detail | [views/card-detail.html:157](views/card-detail.html:157) |
| card-back | [views/card-back.html:99](views/card-back.html:99) |
| board-stats | [views/board-stats.html:185](views/board-stats.html:185) |
| export-time | [views/export-time.html:194](views/export-time.html:194) |
| settings | [views/settings.html:132](views/settings.html:132) |

Кэш токена: in-memory на контекст, обновление за ~5 минут до `exp`, promise-дедупликация — та же
схема, что отлажена в `getBoardId()`/`getBoardSettings()`.

**Сделано иначе, чем планировалось (проще):** регистрировать контекст в шести файлах не понадобилось.
Все вызовы, кроме двух, идут через `TnMStorage`, а туда `t` и так передаётся первым аргументом —
поэтому `useTrelloContext(t)` вставлен в семь методов [js/storage.js](js/storage.js) и дополнительно
в [views/board-stats.html](views/board-stats.html) (единственный view, ходящий в `SupabaseAPI`
напрямую). Остальные пять view и `client.js` не тронуты вовсе.

Покрыто тестом [tests/client_auth_test.mjs](tests/client_auth_test.mjs) (`node tests/client_auth_test.mjs`,
10 проверок): холодный старт, кэш токена, дедупликация 30 параллельных вызовов → один обмен,
перевыпуск за 5 минут до `exp`, фолбэк на anon при падении обмена, фолбэк при незарегистрированном
контексте, и отказ вместо тихого фолбэка при выключенном фича-флаге.

✅ **Проверено в живом Trello (2026-08-29):** `t.jwt()` в контексте колбэков `client.js` есть —
открытие доски даёт `Supabase access token minted` и следом `Prefetched 7 card(s)`. То есть токен
выпущен, PostgREST его принял, политики отдали данные. Строка про минт одна на всю доску —
дедупликация работает, бейджи не плодят по обмену на карточку.

**Опционально (сводится с TODO п.18):** класть токен в `t.set('board','private', …)` — board+member
scope, ровно нужная изоляция (member-scope не годится: токен привязан к доске). Тогда попапы не
минтят свой токен. В первой итерации не делать: это оптимизация, а не безопасность.

**Фича-флаг на время выката:** если минт упал — падать назад на anon-ключ с логом в консоль. Убрать
сразу после Фазы 4, иначе он навсегда останется дырой в обход всей схемы.

## Фаза 3. Политики RLS (01 применён 2026-08-29)

SQL готов, типы подставлены по факту Фазы 0:

- [supabase/sql/01_authenticated_policies.sql](supabase/sql/01_authenticated_policies.sql) —
  хелпер `current_board_id()` + политики для `authenticated`. **Безопасно запускать хоть сейчас:**
  роль пока никем не используется, ничего не ломается.
- [supabase/sql/02_cutover_lock_anon.sql](supabase/sql/02_cutover_lock_anon.sql) — включение RLS на
  `board_settings`, снос политик `"Allow all"` и отзыв грантов у `anon`. **Запускать последним.**
- [supabase/sql/99_rollback.sql](supabase/sql/99_rollback.sql) — мгновенный откат к состоянию
  2026-08-29, без передеплоя клиентов.

Нюансы, заложенные в скрипты:

- `(select public.current_board_id())` в скобках — не косметика: так планировщик считает функцию
  один раз на запрос (InitPlan), а не на каждую строку. Критично для префетча бейджей, который за
  один запрос перебирает все карточки доски.
- Старые `USING (true)` именно **удаляются**: политики одного типа комбинируются через `OR`, любая
  забытая `true` обнулила бы всю схему.
- `revoke ... from anon` — пояс поверх подтяжек на случай, если когда-нибудь по ошибке появится
  разрешающая политика для `anon`.
- Матрица операций сверена с кодом: `boards` S/I · `board_settings` S/I/U · `cards` S/I/U ·
  `time_entries` S/I/D. Чего нет в списке — не покрывается политиками осознанно.
- `sub` в токене — 24-символьный id участника Trello, **не UUID**. Поэтому `auth.uid()` в политиках
  использовать нельзя (упадёт на приведении типа), только `auth.jwt()->>'…'`.

## Что НЕ входит

- Пер-**пользовательские** права (внутри доски все равны). `idMember` кладём в токен на будущее, но
  политики его не используют: в Trello любой участник доски и так видит все карточки.
- Ограничение по роли в доске (observer vs member) — Trello-JWT её не сообщает.
- Разделение prod/dev по данным (п.13, вариант 3): после этой работы теряет смысл — дев-плагин
  получает токен ровно на ту доску, где открыт.
- `t.getRestApi()` в экспорте — отдельный механизм с собственным токеном Trello, не затрагивается.
